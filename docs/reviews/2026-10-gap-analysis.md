# Gap analysis — October 2026

Audit of `main` at `6f387c0` (2026-10-09). Sanitized, public; contains no household data. Companion: [remediation plan](2026-10-remediation-plan.md).

## Method

- Every tracked file (37) was checked by a fast first-pass reviewer, then independently re-read by an advisor reviewer that confirmed, refuted or extended each finding (279 first-pass findings; 50 refuted).
- Seven cross-cutting auditors covered acceptance coverage, code correctness, engineering infrastructure, the GitHub issue backlog, cross-document coherence, privacy/threat model and strategic direction (100 findings).
- Findings were merged into 55 distinct gaps. Each gap was then checked by three independent verifiers (factual, necessity, adversarial-refute). A gap is **verified** only when at least two of three upheld it as true and worth addressing; severity below is the verifiers' median.
- Result: 46 verified, 9 rejected. Verifiers ran tests and scratch probes and read the issues; no live retailer access was attempted. Severity and necessity are reviewer judgment, not measurement.

## Verdict

Agent Household is a specification plus a small set of well-tested, offline
parsing and arithmetic primitives. The code that exists is sound: 62 tests pass,
Ruff is clean, and strict Basedpyright reports only three deprecation errors.
The problems are what is missing and what is recorded as true.

1. **The governing first task has not started in code** (G01). Fourteen merged
   PRs produced Target page-parsing helpers that have no caller and four receipt
   design papers. There is no capability matrix and no reviewed
   transaction/consent model. There is also no code toward the local
   receipt-upload-to-reviewed-expense slice that GOAL_PROMPT.md names as the
   first deliverable (G03, G04, G14).
2. **Foundations are undecided while work builds on them.** P0-03
   (architecture, storage, API, phone contract) and SPEC-00 (threat model,
   roles, retention, keys, agent authority) do not exist (G30, G02, G26, G25).
   Every receipt paper and the newly filed mobile foundation (#67) depend on
   them.
3. **The money path has holes at its seams.** Nothing owns the
   reviewed-receipt → expense/allocation seam. The receipt fact model,
   money lifecycles and the upload → receipt handoff are undefined
   (G16, G18, G20, G21).
4. **Gates are asserted, not enforced.** There is no CI and no committed
   lint/type configuration. The admission rules applied in practice (399-line
   cap, author routes, exact-head review) are absent from the contract, and no
   reviewer is defined (G08, G09, G11, G13).
5. **Status records are false.** BACKLOG.md says implementation has not
   started. Merged papers still call themselves unreviewed or open. Operator
   scope changes (grocery-first, mobile) live only in issues (G05, G06, G35).

Items 4 and 5, the acceptance-coverage gaps and the test-strength gaps are
fixable now; this audit's PR addresses them. Items 1–3 need owner decisions in
the order set out in the remediation plan.

### G16

**Reviewed-receipt → Expense/Allocation seam is owned by no document; acceptance is not bound to an allocation revision; consent actor and partial acceptance are undefined** — high, owner decision.

The review contract hands off to the transaction model ('does not allocate shares, accept debt'), but TRANSACTION_MODEL has no gate between them. Nothing says allocations may leave DRAFT only from a RECONCILED receipt revision, or what happens to PROPOSED/ACCEPTED allocations when a receipt is revised. Expense↔Receipt cardinality and 'distributable total' are undefined; the latter can conflict with the review contract's Σc+U=T. Acceptance is not bound to an immutable allocation revision. Partial (per-participant) acceptance and the DISPUTED/REJECTED exits are undefined. Nothing restricts acceptance to the obligated participant's own actor, as opposed to proposers, agents, templates or preferences. Guest claim/merge provisional status is unspecified.

*Evidence.* receipt-review-contract.md:29 'Receipt review does not allocate shares, accept debt'; :56 Σcᵢ+U=T. TRANSACTION_MODEL.md:13 'Acceptance / Dispute: participants, payer contributions, reviewed shares and consent evidence'; :21 'Partial acceptance must not silently finalize others' obligations'; :26 'reviewed distributable total'. GOAL_PROMPT.md:25 preferences 'never authorize spending'; :37; :41.

*Recommended.* Handle this under P0-02 by editing docs/TRANSACTION_MODEL.md, not by adding a new standalone document. Reuse the existing basket-approval pattern. Write the invariants that follow from existing text now, and list the remaining choices as explicit open decisions. (1) Add a "Receipt → Expense correlation" bullet. A receipt-backed Expense pins an immutable ReceiptRevision, and its allocations leave DRAFT only if that revision is RECONCILED. An Expense with no receipt (manual or cash) needs its own reviewed total and payer/unpaid evidence and goes through the same conservation check. Define distributable total as T of the pinned revision unless an explicitly reviewed exclusion is recorded. Shares must sum exactly to that total, and Σcontributions + U = T stays the review contract's obligation. (2) Make Acceptance bind the authenticated actor, the obligated participant, the immutable AllocationProposal revision, the pinned receipt revision, and the share amount and currency. Any material change to the receipt or the allocation invalidates unsettled acceptances and returns the allocation to PROPOSED. Settled entries are corrected only through attributable Adjustments, as GOAL_PROMPT.md:43 already requires. (3) Define per-participant states (PROPOSED, ACCEPTED, DISPUTED, REJECTED, PROVISIONAL for guests).
